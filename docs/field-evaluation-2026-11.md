# dsh-semantic-drift 现场评估（2026-11）

> **状态**：完成。本文是两个私有项目的落地评估记录，不是实现规格，也不替代基准测试。
>
> **样本**：两个匿名化的 .NET 项目。A 是一个 .NET 类库，处于基础设施完成、准备进入下一阶段的节点；B 是一个 .NET 桌面组件，已有发布与 CI。合计 8 个有效会话、82 轮、2,872 步、4,089 次工具调用。
>
> **数据**：本地 Git 历史、DSH 会话日志（只读）、插件源码的只读复扫。会话日志只取工具调用与结果元数据；未将对话正文用于结论。
>
> **脱敏**：按 [CONTRIBUTING.md](../CONTRIBUTING.md) 的隐私规则，私有项目的项目名、仓库名、模块/命名空间、概念 id、符号名、文件路径、人员与提交哈希均已移除；只保留聚合数字与案例形状。本文不构成 "we tested on X" 的声明。
>
> **结论**：插件已形成可重复的命名治理闭环；当前证据支持“治理效果”，尚不足以支持“缺陷预防效果”。

## 0. 结论摘要

1. **采用**：75 条概念、241 个术语、253 次插件工具调用；创建概念前先查询的比例为 A 100%、B 约 92%；已提交历史中 0 次 id 改名或删除；未发现创建后绕过工具的直接改写。
2. **检测**：43 次扫描调用中 4 次有发现；9 条唯一发现 = 6 条重复类型 + 3 条符号变体；其中 6 条修复（2 个根因）、2 条接受、1 条误报；`contract-drift` 与生产代码命名漂移均为 0。
3. **成本**：词表注入段 0.9k–3.1k tokens/请求，扫描 0.05–1.4s；默认排除项缺少包缓存目录，导致一次全量扫描读入 17.4 MB，补上后为 150 KB。
4. **判断**：它现在更像“低成本的命名护栏 + 可审查的词表”，不是“显著减少缺陷的检测器”。要证明后者，需要 CI 门禁和更长的观察窗。
5. **行动**：见 §7。P0 三项（默认排除项、概念状态、紧凑提示）收益最直接；P1 两项（变更集/CI、批量 upsert）把“偶发扫描”变成“可复现门禁”。

## 1. 样本、方法与边界

### 1.1 样本形状

| 样本 | 形态 | 词表规模 | 会话 | 观察窗 |
|---|---|---|---|---|
| A | .NET 类库，基础设施完成，准备进入下一阶段 | 27 条概念 / 90 个术语 | 2 个有效会话 | 约 9 天 |
| B | .NET 桌面组件，已有发布与 CI | 48 条概念 / 151 个术语 | 6 个会话 | 约 3 天 |

两者合计：82 轮、2,872 步、4,089 次工具调用、253 次插件工具调用。

### 1.2 数据来源

- **Git 历史**：词表文件的提交序列、概念增删、是否与代码同提交。
- **DSH 会话日志**：`tool/call` 与 `tool/result` 的时间、参数、结果；会话标题与注入的提示段。
- **只读复扫**：用当前扫描器对两个工作区做交叉验证；词表经简化解析后传入，27/48 条概念均解析成功。
- **项目内文档**：词表说明、架构规则、路线图（只取与命名治理相关的部分）。

### 1.3 边界

- **不是对照实验**：没有“无插件”的平行组，无法把命名一致性完全归因于插件。
- **样本小、周期短**：两个项目、一个开发者、3–9 天；结论是案例研究，不是统计显著。
- **检测器是词法级**：完全改名的漂移、行为漂移、文档漂移不在现有检测范围内。
- **历史扫描多为高置信度**：当前复扫用 medium/low 交叉验证；两者不能直接混算。
- **没有每会话 token 归因**：DSH 用量账本按天/按 provider 聚合；本文只给单请求估算。
- **面板/UI 操作不在日志里**：如果有人在面板里改词表或接受例外，工具调用统计会漏掉。

### 1.4 脱敏规则

- 项目、仓库、模块、命名空间、概念 id、符号名、文件路径全部替换为形状描述；
- 不出现本机绝对路径（macOS、Linux 或 Windows 的用户目录）；
- 不出现提交哈希、人员、外部链接；
- 只保留“多少个、多快、占比多少”这类可复现数字；
- 不使用“我们在 X 上测试”的句式；数字描述发生了什么，不描述在哪里发生。

### 2.1 采用是真实的

- 插件调用占工具调用的 **2.8% / 8.0%**，不是“装了就忘”。
- 两个项目的词表都随代码提交，且 **0 次已提交的 id 改名/删除**；概念 id 是稳定的。
- **创建后 0 次绕过工具直接改写词表**：A 的初始 18 条由一次直接写入建立（引导期），之后全部走 `semantic_upsert`；B 未观察到直接改写。
- B 的 48 个 canonical symbol **全部在源码中出现**；A 的 15 个已实现符号也全部出现。词表不是“写完就烂在仓库里”的文档。

### 2.2 覆盖要分两种口径

- **A：设计契约覆盖**。27 条概念里 12 条尚未实现（约 44%）；源码目录里 15 个 public class/interface/enum/struct 中 14 个与词表一致（93%）。这里的“覆盖率”应理解为“下一阶段的设计契约已登记”，不是“已落地比例”。
- **B：API 覆盖**。48/48 个符号存在；51 个 public 类型中 39 个是 canonical 概念（76%）。未登记的 10 个主要是 event args、options、factory、registry 这类非领域概念；另有 2 个公共复数工厂名是带理由接受的。这个比例是否“够”，取决于词表的范围规则——插件 README 明确说它是概念词表，不是类型大全。

## 3. 效果：抓到了什么，没抓到什么

### 3.1 三个完整闭环

**案例 1：重复的私有 delegate helper（A）**

一次扫描报出 5 条 `duplicate-type`：同一个私有 delegate helper 同时定义在 5 个测试编译单元和 1 个基准测试单元中。随后把基准测试里的副本改名，复扫归零；从扫描结果到提交约 **15 秒**。提交信息明确把“避免被 drift 扫描视为重复”作为原因。

这个案例的形状是“辅助代码重复”，不是生产契约分叉。它的价值是减少复制粘贴和歧义命名，而不是阻止一次线上故障。

**案例 2：重复的测试 fake + 包缓存误报（B）**

同一次扫描报出两条：一条是同一个测试 fake 在两个测试项目里重复定义（真实重复），另一条是包缓存 XML 文档里的符号变体（误报）。当天把其中一个 fake 改名，并把包缓存目录加入词表排除项；从扫描到提交约 **2 小时**。

这个案例同时暴露了两件事：重复类型检测器是有效的；默认排除项不覆盖包缓存，会让新项目在第一次全量扫描时读到大量无关 XML。

**案例 3：公共复数工厂名（B）**

一次扫描报出两个 `symbol-variant`：两个公共复数工厂名与各自的单数 canonical symbol 不一致。两条都用 `semantic_accept` 接受，理由写明是已发布的公共工厂类，复数名用于区分“类型”和“内置实例目录”；4 分钟后复扫归零。当前扫描仍显示 **2 条被静音**，说明例外机制在持续工作，而不是一次性配置。

### 3.2 汇总

| 指标 | 数值 |
|---|---|
| 扫描调用 | 43 |
| 有发现的扫描 | 4（9.3%，含并行会话的重复调用） |
| 唯一发现 | 9（6 duplicate-type + 3 symbol-variant） |
| 修复 | 6 条 / 2 个根因 |
| 接受 | 2 条 |
| 误报 | 1 条 |
| `contract-drift` | 0 |
| 生产代码命名漂移 | 0 |

### 3.3 怎么解读

- **精度可以接受**：9 条里 6 条对应真实重复，2 条是刻意保留并记录理由的公共命名，1 条是包缓存噪声。按“可行动”口径，8/9 有明确处理。
- **召回未知**：0 条 `contract-drift` 不等于“没有漂移”。两个仓库分别只有 15 / 51 个公共类型，检测机会少；完全改名的漂移也不在词法检测器范围内。
- **价值主要在一致性**：真正的产出是“每次改动后有一个确定性的检查 + 一份可 review 的词表”，而不是“抓到了多少 bug”。这也是为什么案例都落在测试/基准辅助代码，而不是生产契约。

## 4. 成本

### 4.1 提示成本

| 样本 | 当时概念数 | 注入段 | 占系统提示正文 | 估算 tokens |
|---|---|---|---|---|
| A | 24 | 2,790 字符 / 34 行 | 33% | ≈0.9k |
| B | 48 | 9,362 字符 / 58 行 | 62% | ≈3.1k |

加上固定的 5 个工具 schema（5,474 字符，约 1.4k–1.8k tokens），每请求大约多 **2.4k / 4.6k tokens**（未计缓存）。系统提示命中缓存时边际成本会低很多，但改词表或切工作区会让缓存失效。

与 README 的 18 概念 / 1,749 字符基准基本一致：增长近似线性，主要受 note 长度影响；48 概念时 58 行，尚未触及 200 行上限。

### 4.2 扫描成本

| 场景 | 文件数 | 字节 | 耗时 |
|---|---|---|---|
| A 历史 | 9–30 | 25–148 KB | 13–112 ms |
| B 历史全量 | 242–292 | — | 0.77–1.38 s |
| B 历史限定路径 | 66–67 | — | 49–79 ms |
| A 当前（默认排除） | 154 | 17.4 MB | 647 ms |
| A 当前（补包缓存排除） | 33 | 150 KB | 49 ms |
| B 当前 | 67 | 458 KB | 114 ms |

关键发现：**默认排除项不覆盖包缓存目录**。两个项目都在本地带包缓存，规模从数百 MB 到数 GB；扫描器只读文本类文件也会读入 17.4 MB。补一条 `.nuget/**` 后降到 150 KB，耗时从 647 ms 降到 49 ms，误报也消失。这不是某个项目的特殊配置，而是 .NET 仓库的通用形状，应该进入默认排除项。

### 4.3 写入摩擦

- 14 次 `semantic_upsert` 失败：12 次是同一批概念 id 没有点号（`id-format`），2 次是术语重复（`term-duplicate`）。
- 校验全部在写入前拒绝，**没有产生坏数据**；12 次 id 失败与 2 次术语冲突都在修正后重试成功。
- 成本是 12 次往返和一轮上下文；如果支持批量 upsert，或在错误里直接给出“把 `flat_name` 改成 `group.name`”的建议，这个成本可以降到接近 0。

## 5. 治理质量

| 维度 | 观测 |
|---|---|
| 单写路径 | 0 次创建后手改；全部走 `semantic_upsert` |
| id 稳定性 | 0 次已提交改名/删除；75 条概念只增不减 |
| 例外 | 2 条，均带路径与理由；当前仍静音 2 条 |
| 提交 | 6 + 6 次词表变更，全部随功能/文档提交 |
| 文档 | 一个项目有词表说明 + 架构规则；另一个主要靠注入提示 |
| 文档漂移 | 一个项目的词表说明仍写 24 条，实际 27 条 |

几个判断：

- **词表是“活”的，不是一次性文档**：两个项目都在功能推进中持续登记，A 从 18 到 27、B 从 19 到 48，均有提交对应。
- **例外机制按设计工作**：2 条例外都有最小范围（具体文件）和理由，当前扫描确实各静音 1 条；这比“在配置里全局忽略”更可审计。
- **但提交粒度偏粗**：所有词表变更都混在功能/文档提交里，没有单独的“只改词表”提交。review 时词表 diff 容易被代码 diff 淹没；这与其中一个项目自己写的“词表变更单独小提交”规则也不完全一致。
- **词表自己的说明会过期**：一个项目的词表说明仍写着旧计数（24 vs 27）。插件不检查这种“关于词表的文档”的漂移，这是一个真实的元数据缺口。

## 6. 判断

| 维度 | 判断 | 依据 |
|---|---|---|
| 词表治理 | **强** | 75 概念、241 术语、0 已提交改名、0 手改 |
| 命名闭环 | **中上** | 92–100% 先查后建；12 次 id 格式失败暴露 UX 摩擦 |
| 漂移检测 | **中** | 2 个真实根因、1 个误报、0 生产契约漂移 |
| 例外机制 | **强** | 2 条带理由，当前仍静音 2 条 |
| 成本 | **可接受** | 扫描 0.05–1.4s；提示 2.4–4.6k tokens/请求 |
| 行为漂移 | **未验证** | 仍在路线图阶段 |

**一句话**：这两个项目足以证明插件“能用、有人用、有治理效果”，但还不足以证明“能显著减少缺陷”。

如果要改变这个判断，需要三样东西：

1. 一个 **CI 门禁**，把“会话中偶发扫描”变成“每个变更都检查”；
2. 一个 **更长的观察窗**（至少 4–6 周），覆盖一次命名密集的迭代；
3. 一个 **可比的对照**（同一模块的前后对比，或两个相似模块的并行对比）。

## 7. 建议清单

> 成本口径：S ≤ 1 天，M 2–3 天，L 1–2 周（单人，含测试与文档）。收益尽量用本次观测到的数字，不写“应该会更好”。

### P0 — 先做，收益立竿见影

- [ ] **P0-1 补默认排除项**
  - **做法**：把 `.nuget/**`、`artifacts/**`、`.tmp/**`、`TestResults/**`、`BenchmarkDotNet.Artifacts/**` 加入默认排除项；`packages/**` 按生态决定（JS monorepo 可能把它当源码），至少不要在 .NET 模板里漏掉包缓存。保留用户可编辑的 `exclude` 覆盖。
  - **收益**：A 的全量扫描从 154 文件/17.4 MB/647 ms 降到 33 文件/150 KB/49 ms；包缓存误报消失；新 .NET 仓库开箱即用，不必每个项目手补一条。
  - **验收**：带包缓存的 fixture 全量扫描 < 1 s，且不产生来自缓存的发现；补一条回归测试。
  - **成本**：S。

- [ ] **P0-2 概念状态 `planned | active | deprecated`**
  - **做法**：给概念加可选 `status`（默认 `active`）；`planned` 不参与覆盖率、不触发 `term-unmapped`；提示段用紧凑标记展示状态；v1 词表保持前向兼容。
  - **收益**：A 的 12 条“已登记未实现”概念不再被误算成“已落地”；当前 3 条 low 误报（中文通用词）可以直接消失；路线图与词表合一，下一阶段推进时能看到“哪些契约已冻结、哪些还没实现”。
  - **验收**：A 的 12 条标记为 `planned` 后，覆盖率报告从 27 条口径变为 15 条口径；`term-unmapped` 不再报这 3 条；`active` 行为不变。
  - **成本**：M。

- [ ] **P0-3 紧凑提示模式**
  - **做法**：增加 `announceDetail: full | compact`；`compact` 只注入 `id -> symbol`，不带 note；默认保持 `full`。
  - **收益**：B 的注入段可从 9,362 字符降到约 3,000 字符（约 −68%）；大词表项目的每请求成本显著下降。
  - **验收**：同一词表下 compact 输出 ≤ full 的 50%；开关切换不需要重载；两种模式都不超过 200 行。
  - **成本**：S。

### P1 — 把“偶发扫描”变成“可复现门禁”

- [ ] **P1-1 变更集扫描 + CLI + CI**
  - **做法**：增加只读 CLI（如 `scan --changed`，基于 git diff 的变更文件）；提供 GitHub Action 示例；medium+ 的新发现让 CI 失败；支持 `--json` 供机器读取。
  - **收益**：本次 43 次扫描全是会话中手动触发，两个项目 0 个 drift 门禁；CI 化后每个 PR 都能检查，发现数、误报数、修复时延可以按周统计；不需要 watcher/daemon，符合现有“按需扫描”的承诺。
  - **验收**：在一个有 CI 的项目上，刻意植入的变体能让检查失败；只改一个文件时，扫描 < 5 s；无变更时直接退出 0。
  - **成本**：M。

- [ ] **P1-2 批量 upsert / id 前缀助手**
  - **做法**：`semantic_upsert` 接受数组（逐条校验、逐条返回 issue）；或在 `id-format` 错误里给出“建议 id”；可选 `defaultGroup`，把 `flat_name` 自动补成 `group.flat_name`。
  - **收益**：B 首次批量登记时的 12 次 `id-format` 失败可以合并成 1 次调用；新项目接入更快，减少上下文往返和 token 消耗。
  - **验收**：12 条概念一次调用创建；单条失败不影响其他条；每条 issue 仍有位置。
  - **成本**：M。

### P2 — 让效果可持续测量

- [ ] **P2-1 可选的指标导出**
  - **做法**：按工作区统计扫描次数、发现/接受/静音数、平均耗时；面板展示最近 N 次趋势；或提供只读 JSON 导出；默认不写盘、不上传。
  - **收益**：现在所有指标都要从会话日志反推；有了导出，“0 发现”能区分“干净”和“没扫”，发布说明也能引用真实数字。
  - **验收**：导出最近 30 天统计；默认关闭；开启后只写一个可 gitignore 的本地文件。
  - **成本**：M。

- [ ] **P2-2 行为漂移**
  - **做法**：按 [behavior-drift-roadmap.md](behavior-drift-roadmap.md) 推进：先 C#、先 watch 的函数；确定性指纹 + Agent proposal + 人工审核；opt-in。

## 8. 后续测量计划（2 周）

如果要把“案例研究”升级成“可比较的评估”，建议在下一阶段做一次 2 周基线，不改代码，只采集：

| 指标 | 定义 | 目标/用途 |
|---|---|---|
| 先查后建率 | 创建概念前有同 id/symbol 的 `semantic_get` | ≥ 90% |
| 词表覆盖率 | canonical 概念 / 已实现 public 类型 | 区分 active 与 planned |
| 扫描命中率 | 有发现的扫描 / 总扫描 | 观察是否长期为 0 |
| 发现→修复时延 | 扫描时间 → 提交/复扫归零 | 中位数 < 1 天 |
| 误报率 | 人工判定为噪声的发现 / 总发现 | < 20% |
| 提示成本 | 注入段字符数 / 估算 tokens | compact 后 −50% |
| 命名返工 | review 中因命名被要求改的次数 | 作为“缺陷预防”的代理指标 |

三个预注册假设：

1. 加 CI 门禁后，每个 100 次提交至少能暴露 1 条可行动发现，或把“生产命名返工”降到 0；
2. 加 `planned` 状态后，A 的 12 条未实现概念不再计入覆盖率，3 条 low 误报消失；
3. compact 模式把注入段压到 full 的 50% 以下，且先查后建率不下降。

如果 2 周后仍然 0 发现、0 命名返工，那么更合理的结论是：**这个插件在当前项目里是“保险”，不是“检测器”**；是否继续投入行为漂移，应该按“保险价值”而不是“抓错数量”来判断。

## 附录 A：指标定义

- **先查后建**：一次 `semantic_upsert`（created=true）之前，同一会话内存在同 `id` 或同 `symbol` 的 `semantic_get`。
- **唯一发现**：按 detector + symbol + 主路径去重；同一根因的多个实例仍计为多条发现，但另记“根因”。
- **修复时延**：扫描结果时间 → 对应提交时间；如果没有提交，用下一次复扫归零的时间。
- **覆盖率**：canonical symbol 作为 public type 名出现的数量 / 源码目录下 public class/interface/enum/struct 声明数；delegate 未计入，属于已知低估。
- **注入段**：系统提示中从 `## Project vocabulary` 到最后一条概念行的文本；不含工具 schema。
- **扫描范围**：扫描器实际读取的文件数与字节数；不是仓库总大小。
